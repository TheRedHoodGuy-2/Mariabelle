2. Account Structure
2.1 Two-Account Model
CRITICAL ARCHITECTURAL DECISION: Never run automation on your main account. Operate two separate accounts.
MAIN ACCOUNT	Your personal WhatsApp number + Discord account. This is your VAULT. Holds all accumulated wealth (bank balance, high-tier cards). Minimal bot activity. Manual play only. Never automate this account.
BOT ACCOUNT	Dedicated WhatsApp SIM (separate number) + Discord account. Runs ALL automation 24/7. Earns coins and cards continuously. You manually transfer assets to MAIN periodically.
Transfer method	YOU manually send .donate [amount] or .sc [@main] [card_index] [price] from the bot account when you decide to. No automated transfer — keeps it looking human.
Why this matters	If bot account gets banned, you lose nothing. All wealth is safely on main. Bot account is replaceable. Main account is irreplaceable.
2.2 Number Change Procedure
If the bot WhatsApp number gets banned:
1.	Get a new SIM/number
2.	Delete old Baileys session file
3.	Re-authenticate Baileys with new number
4.	Run this SQL: UPDATE all tables SET player_id = 'new_number' WHERE player_id = 'old_number'
5.	Bot resumes exactly where it left off — all data preserved in Supabase
Note: The Tensura profile IS tied to the WhatsApp number at the server level. A banned number loses its Tensura profile. This is why the main account (vault) must never run automation and must never get banned.

  last_seen     timestamptz,
  updated_at    timestamptz default now()

Every gambling outcome across all groups and platforms.
gambling_events (
  id              uuid primary key default gen_random_uuid(),
  player_id       text not null,
  player_name     text,

  game            text not null,    -- casino|slots|coinflip|dice|db|roulette|horse|dp

5. Bot Logic: Gambling Data Collector
This module is PASSIVE — it watches and records. It never places bets. It runs on both WhatsApp and Discord simultaneously.
5.1 Games Detected
.casino <amount>	Simple double-or-nothing. Most popular game. Win = 2x bet.
.cf <heads|tails> <amount>	Coinflip. Guess heads or tails.
.slots <amount>	Slot machine. Win = 2x bet.
.dice <1-6> <amount>	Guess the dice roll (1-6). Win = 3x bet.
.db <amount>	Dice battle vs Rimuru. Both roll, higher wins. Draw possible = refund.
.roulette <type> <amount>	Roulette with bet types.
.horse <selection> <amount>	Horse racing (mechanics not yet fully documented).
.dp <amount>	Unknown mechanic — log raw responses until understood.
5.2 Command Detection
Listen for all messages matching the command patterns above. On match, create a pending_bet record:
pending_bet = {
  id:           uuid,
  message_id:   original message ID,   // KEY for reply matching
  player_id:    sender phone/Discord ID,
  player_name:  sender display name,
  platform:     whatsapp | discord,
  group_id:     group/channel identifier,
  game:         detected game type,
  bet_amount:   parsed from command,
  guess:        heads/tails or 1-6 (if applicable),
  status:       pending,
  created_at:   now()
}
Queue keyed by: group_id + player_id + game + bet_amount (FIFO per key, handles spam/multi-group same-bet scenarios).
5.3 Bot Reply Matching (Priority Order)
PRIORITY 1 — Quoted/replied message (most reliable):
Bot reply quotes a message → look up pending_bet by quoted message_id → direct 1:1 match → resolve immediately
PRIORITY 2 — Player mention + game + amount:
Bot reply mentions player name → match by player_id + game + bet_amount + group_id → pop oldest from FIFO queue → resolve
PRIORITY 3 — Orphan queue:
No clean match → store as orphan → retry matching every 30s → expire after 10 mins → mark unresolved
5.4 Outcome Parsing — Exact Bot Response Patterns
WIN patterns:
"You win! +X coins!"
"You won X coins!"
"You guessed it right! You win X coins!"
LOSS patterns:
"You lost. Better luck next time!"
"You lost X coins. Better luck next time!"
"You guessed wrong. Better luck next time!"
DRAW pattern (.db only):
"It's a tie! Your bet has been refunded."
PASSIVE INCOME (route to passive_income_events, NOT gambling):
"A stranger flicked X coins at you"
"A quest giver handed you X coins"
"Someone tipped X coins"
5.5 Cross-Group / Spam Bet Handling
Players sometimes bet in Group A (high ping, no reply) then repeat in Group B. These are TWO separate events on two separate group_ids. Log both independently. The FIFO queue per group_id prevents cross-contamination. Flag players who consistently cross-group-bet as cross_group_bettor: true for intelligence value.
5.6 Pending Bet Expiry
Pending bets expire after 10 minutes with no reply → mark status: expired, reason: timeout. Global send queue enforces minimum 500ms gap between ANY outgoing message across ALL groups to prevent WhatsApp rate limiting.

 
6. Bot Logic: Card Claimer
Target: 90% claim rate. The card claimer is the single highest ROI feature of the entire system.
6.1 Card Spawn Message Format
WhatsApp — image + caption:
🎊 A wild card has appeared! 🎊

Name: Wilhelm van Astrea
Tier: 3
Price: $19911
Spawn ID: 561ca          ← 5-char alphanumeric
Issue: #1

Claim it with .claim 561ca
Discord — embed format:
Title: "A wild card has appeared!"
Fields: Name, Tier, Price, Issue
Card artwork image
Footer: "Claim it with .claim 94650"   ← numeric only on Discord
Spawn ID extraction regex (works for both platforms):
/\.claim\s+([a-zA-Z0-9]+)/
6.2 Humanised Delay Distribution
DO NOT use flat Math.random(). Use weighted distribution that mimics human reaction:
1500ms – 2500ms	20% probability — fast, rare
2500ms – 4000ms	50% probability — normal, peak zone
4000ms – 6000ms	25% probability — slow, occasional
6000ms – 9000ms	5% probability — very slow, rare
Adjust by group competition score: low competition groups → shift distribution 500ms faster. High competition → use base distribution as-is.
6.3 Offline Recovery Flow
When .claim is sent but no bot reply arrives:
T+0s:   .claim [spawn_id] sent — no reply
T+5s:   resend .claim [same spawn_id]
T+20s:  if still no reply → send .test
T+50s:  if .test no reply → send .bots
T+60s:  if .bots no reply → one final .claim attempt
T+70s:  give up → mark outcome: unresolved_offline
When bot comes back ONLINE after offline period:
→ Send .col or .si to reconcile collection
→ Compare against last known collection state
→ Any new cards = successful offline claim → update outcome to claimed
6.4 Group Competition Scoring
Per group, maintain rolling stats used to prioritise groups and adjust claim speed:
group_score = (
  cards_per_hour              * 0.5 +
  our_claim_rate              * 0.3 +
  (1 / avg_competitor_speed)  * 0.2
)
High competition flag: if gap between winner and our bot is consistently < 300ms → another bot is likely present in that group. Log as suspected_bot_group and consider deprioritising.
6.5 Miss Tracking
On every miss log: card name, tier, group_id, spawn time, who claimed it, their speed, our delay, the gap. This data drives group scoring and delay optimisation over time.

 
7. Bot Logic: Daily, Fishing & Digging
7.1 Daily (.daily)
Per-group independent tracking. Never miss — streak loss is the worst possible outcome.
On startup: check last_daily_at from Supabase per group
If > 24h since last claim → send .daily immediately
Parse response: "claimed your daily reward of X coins + Y streak bonus (streak: Z)"
Log: amount, streak_bonus, streak_count, group_id, timestamp
Schedule next: now + 24h per group

If bot offline when daily is due:
  → retry every 30 minutes
  → after 3 failed retries: alert via Discord private channel
  → never skip
7.2 Fishing (.fish + .sell fish)
5–20 attempts per hour per group. Each group has independent scheduler.
Interval between casts (weighted):
3–5 min gap	20% probability
5–7 min gap	50% probability — peak
7–10 min gap	25% probability
10–12 min gap	5% probability
Gives approximately 10–12 casts per hour average.
Catch routing:
fish caught  → immediately send .sell fish → log coins earned
item caught  → log item type, hold for future routing
card caught  → treat as card claim, log tier + name
nothing      → log miss, schedule next attempt
on cooldown  → parse exact wait time, schedule precisely (subtract 5s to avoid drift)
7.3 Digging (.dig)
Same scheduler pattern as fishing. Confirmed response format:
"You used your Shovel and dug up:"
[coin image] $241 Coins
Bot response is a MEDIA message (image + caption text). Parse coins from caption. Cooldown duration unknown — learn from first responses and schedule accordingly. Store raw_response for all dig results until patterns are fully understood.
7.4 Cooldown Checking (.cds)
.cds shows cooldown status for all commands. Run .cds on startup per group to immediately know when each command is next available, rather than waiting to discover cooldowns organically.

 
8. Bot Health Monitor
One bot per WhatsApp group (confirmed). Multiple bots possible per Discord server. State machine runs independently per group.
8.1 Five-State Machine
ONLINE	Bot messages arriving normally. All automation runs.
SUSPICIOUS	No bot reply for 3+ min (high-activity) or 10+ min (low-activity) while commands are being sent. One .test command sent. Waiting up to 10 min for any reply.
OFFLINE	No reply to .test after 10 min wait. ALL automation stopped. Passive listening only. Waiting for any bot message.
RECOVERING	Bot message received after offline. Wait 60s to confirm stability. Reconcile collection (.col). Flush missed dailies. Resume automation. Transition to ONLINE.
PARTIAL_OUTAGE	.test replies (bot alive) but specific command types have 0 replies in 30 min in an active group. Only suspend failing command types. Keep other automations running.
8.2 Activity-Aware Trigger
Only enter SUSPICIOUS state if: (1) other users ARE sending commands in the group (group is active) AND (2) the bot is not replying to ANY of them. If the group is simply quiet, do not trigger — bot may be fine.
8.3 Dynamic Bot Detection
Never hardcode bot phone numbers or Discord IDs. Detect dynamically:
WhatsApp: parse .bots command response. Extract bot names and their sender phone numbers. Store in known_bots table. Any new bot appearing in .bots response that is not in the table gets added automatically. If a number changes, old entry goes inactive, new one is added on next .bots parse.
Discord: use author.bot === true flag (discord.js native). No hardcoding needed. Store bot username + snowflake ID in known_bots table.
8.4 .bots Response Format
Confirmed format from screenshot:
TENSURA
  └─ BOTS
      ├─ ALYA    🟢  (green = online)
      ├─ MEGUMIN 🔴  (red = offline)
      ...
Parse this to update bot_health status for all bots in the group. Run .bots check once after 3 minutes of no bot messages (when commands ARE being sent). If no reply to .bots after 10 minutes → mark OFFLINE.

12. Discord Specifics
12.1 Self-Bot vs Observer Bot
Discord uses TWO separate processes running simultaneously:
Self-bot (YOUR token)	Automates commands as your real Discord account. Sends .daily, .fish, .claim, .casino etc. Uses discord.js-selfbot-v13 library. This earns coins and cards on YOUR profile.
Observer bot (app token)	Silent discord.js bot account. Never sends commands. Just listens, logs all messages to Supabase, monitors bot health. Purely intelligence gathering.
Why both?	Self-bot = earner. Observer = brain. Combined they give full automation + full data.
Risk note	Self-botting is against Discord ToS but extremely low ban risk if behaviour looks human. Use humanised delays same as WhatsApp.
